文件服务自己部署，究竟多了哪些选择和责任？

出品：王福强 · 把文件这件事儿，理顺！

“资料放在哪里，能不能自己定？”

这是考虑自部署的一个很实际的理由。团队已有运行环境，或者对存储位置、访问方式有自己的要求，就会想把文件服务也安排进去。

但选择多了，事情也要有人管。谁建账号，谁处理容量不足，升级谁来做，出了故障找谁？这些都会进入日常使用的成本。

FooCloud(https://keevol.cn#foocloud) 提供自部署试用入口。值不值得采用，可以从一轮小试点看起，把便利和后续工作一起算清楚。

启动服务之后，谁负责哪一段

普通使用者关心登录后能不能做事：资料找得到，换电脑接得上，发给客户的入口能管理。

团队管理员要安排成员和空间：谁能进来，哪些资料只供查阅，哪些目录需要持续修改。

部署负责人则要让服务持续可用：网络、存储、升级、备份、故障恢复，都得有安排。

这些事可以由一个人承担，也可以分工，不要求为了用软件专门设几个岗位。但职责得有人接。

否则很容易各自觉得已经完成：部署的人把页面打开了，使用者却还不知道目录在哪；使用者以为装好就能在家连，负责人还没安排外部访问。

这些落差，试点时就值得暴露出来。

本机跑起来，再让第二台接上

公开试用说明沿用了 FSCloud 的旧名称，面向有自部署经验的人：准备 Docker，取得 Compose 配置，启动后从本机 Web 入口体验，并在配置页取得 macOS 客户端。

先这样看看产品，很合适。要试跨设备，还得多走一步。

本机地址只指向当前电脑。把这个地址原样填到另一台电脑上，不会自动连回第一台。负责人需要提供两台设备都可访问的服务地址，并准备客户端同步所需的网络条件。

所以可以分两轮：第一轮在本机登录、上传，熟悉界面；第二轮接入另一台电脑，完成一次真正的文件往返。

默认试用配置使用公开的试用凭据和本机体验设定，不能原样视为正式公网方案。进入团队或外网使用前，访问保护、凭据和连接方式，要由负责环境的人按实际情况安排。

普通使用者拿到能用的入口，再验证自己的工作就好。没必要为了试文件工具，先人人学一遍部署。

自己能决定，也意味着自己要安排

运行位置、存储、访问方式能按自己的条件选，这对有相应需求的团队有价值。

如果最想要的是尽快开工、少做环境维护，也值得认真比较托管服务。坚果云团队功能强调减少自建文件服务的维护负担，回应的就是这种需求。

我们不觉得所有团队都该选同一种方式。已有机器能启动服务，是一个起点；之后谁看容量、谁验证升级、谁检查备份，仍然会占用时间。

预算里把这些工作写出来，自部署的选择才算做完整了。

另外，服务放在自己的环境里，并不意味着资料永远只留在那里。客户端会同步，接收方会下载，外部 Agent 也有自己的数据处理方式。实际怎么流转，要沿着工作过程看，不能单靠“自部署”三个字下结论。

扩大之前，留下一张责任清单

先写使用范围：哪些人、哪些设备、哪些目录。范围明确，试用结果才有对应的工作场景。

再写访问条件：办公室、家里、出差时分别怎样连接，中断了找谁。拿实际会用的设备和网络验证，比只在部署机器上打开一次页面更有说服力。

接着写维护责任：升级、容量、运行状态由谁看，其他人知道怎样联系吗？最后写恢复准备：是否在独立环境里恢复过，需要的文件和版本能否打开？

这几项可以和试用任务清单放在一起。使用者看体验，管理员看访问范围，部署负责人看运行条件，再决定增加多少人、多少资料。

先让一个小项目稳定地用起来。能持续承担的范围有多大，资料就逐步放到多大。
